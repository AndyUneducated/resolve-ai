# Multi-agent vs single-agent for customer support: a benchmarked trade-off study

_Draft title:_ **Multi-agent vs single-agent for customer support: a benchmarked trade-off study**

## Thesis

"Use multiple agents" and "use Plan-and-Execute" are architecture decisions, not
defaults. They each cost something (more LLM calls, more orchestration) and they
each buy something (cheaper routing, fewer wrong tool calls, higher resolution
rate). This study measures the costs and benefits on a fixed benchmark so every
trade-off can be defended with numbers rather than vibes.

## What we vary

Four configurations, each run against the same 120-ticket benchmark
(`apps/api/tests/fixtures/benchmark_tickets.jsonl`, 60% billing / 30% technical /
10% escalation, each ticket carrying ground-truth intent, resolution path,
expected tool calls, and a resolution rubric):

| Variant | Topology | Handoff | Business strategy | Triage tier | Tests |
|---|---|---|---|---|---|
| **A** | single agent | — | ReAct | vertical | Is multi-agent worth it at all? |
| **B** | 4 agents | full transcript | Plan-Execute | triage | Value of a *structured* ticket summary at handoff |
| **C** | 4 agents | structured | ReAct | triage | Value of Plan-and-Execute over single-step ReAct |
| **D** | 4 agents | structured | Plan-Execute | triage | The shipped configuration (baseline) |

Plus a cost-routing micro-ablation: **D** (triage on the cheap tier) vs
**D_triage_vertical** (triage forced onto the expensive vertical tier).

## How we measure

- **Tokens** are real, captured from the local Ollama runs via a contextvar
  trace (`core/usage.py`) that buckets every chat-model call — including nested
  Plan-Execute sub-graph and structured-output calls — by cost tier.
- **$/ticket** is *modeled*: each cost tier is priced at a representative
  Anthropic list price (triage ≈ Haiku, vertical ≈ Sonnet). Token counts are
  real; only the dollar conversion is a model, which keeps the benchmark free and
  reproducible while still surfacing the economics of cost routing.
- **Latency** is end-to-end wall clock per ticket (P50 / P95).
- **Auto-resolution** is judged by an LLM judge (`eval/judge.py`) against each
  ticket's rubric; the judge runs *outside* the token-capture window so it never
  contaminates a variant's token/cost numbers.
- **Tool error** = any failed/blocked tool call, a wrong-tool selection (a tool
  called that is not in the ticket's expected set), or a hallucinated entity flag.
- Runs invoke the compiled LangGraph **directly, without the guardrail wrapper**,
  so the numbers reflect the agent architecture rather than the (constant,
  M5-owned) guardrail layer — notably the vertical-tier policy judge.

Reproduce with:

```bash
uv run python scripts/eval_architecture.py --variants A,B,C,D --cost-routing
```

## Failure-mode report

For each variant we keep the 1-2 worst cases (lowest judge score / errors) and
write up *why* that configuration failed on that ticket. Expected patterns to
discuss honestly:

- **A (single agent)**: wrong-tool selection across the full 12-tool surface
  (e.g. reaching for Stripe on a technical ticket); over-eager refunds without
  the billing-specific guardrail framing.
- **B (full transcript)**: token blow-up on long tickets; planner distracted by
  irrelevant conversation history vs the compact structured summary.
- **C (ReAct)**: missing a step that Plan-and-Execute would have ordered (e.g.
  refunding before verifying the charge), or burning the step budget.
- **D**: where it still loses — e.g. tickets needing KB grounding the single
  agent could improvise, or pure policy questions where the extra hop adds
  latency with no resolution benefit.

## Honesty section

Dimensions where multi-agent shows **no** gain are reported, not hidden. If, for
example, B's structured-handoff token savings are small on short tickets, or D's
latency is worse than A's because of the triage hop, that is the trade-off — and
naming it is the senior signal this study is built to produce.
